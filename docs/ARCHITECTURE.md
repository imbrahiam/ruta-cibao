# Architecture

What exists today, and where the rest is going. Sections marked **Planned**
describe decisions that are settled but not yet built.

## Request paths

Three handlers live under `/api`, and Next resolves literal segments before the
catch-all, so they do not collide:

| Path | Handler | Audience |
| --- | --- | --- |
| `/api/auth/*` | Better Auth | Sign-in flows |
| `/api/rpc/*` | oRPC `RPCHandler` | This app's typed client only |
| `/api/*` | oRPC `OpenAPIHandler` | Third parties, plus `/api/docs` and `/api/spec.json` |

One router (`src/orpc/router.ts`) feeds both oRPC handlers, so the REST surface
and the OpenAPI document can never drift from the RPC one. Publishing a usable
API is a contest deliverable, which is why the spec is generated rather than
written.

`/api/rpc` accepts no GET. oRPC v2 refuses it by default, and rightly: a
procedure reachable by GET is reachable from a cross-site `<img>` or `<script>`
tag, which would mean taking on CSRF protection for no benefit.

The oRPC packages are pinned to `2.0.0-beta.32`. v2 is where the library is
going and its OpenAPI story is the one this project needs; the cost is a beta
whose API can shift between releases, so every `@orpc/*` version is pinned
exactly rather than tracking the `beta` tag.

Large binary responses — vector tiles, PDF and GPX downloads — will use plain
route handlers instead of oRPC, since they are not JSON-shaped.

## Layers

```
src/app/        routes and UI
src/orpc/       procedures, request context, permission middleware
src/modules/    domain services — typed commands, Zod contracts   (planned)
src/db/         Drizzle schema, connection pool, migrations
src/lib/        adapters and cross-cutting helpers
```

Business rules belong in `src/modules`, not in route handlers. Validation is
concentrated at the edges — oRPC inputs, env parsing, the JCE response — so
everything inside works with types that are already known to be good.

## Configuration

`src/lib/env.ts` parses `process.env` with Zod and caches the result. Validation
is lazy so `next build` needs no configuration and no secret is ever baked into
an image layer; `src/instrumentation.ts` forces the check when the server boots,
so a misconfigured deployment fails to start instead of failing a request.

Anything environment-specific goes through an adapter, which is what lets the
same image run on a VPS or on Railway: storage (MinIO / S3 / R2), map tiles,
geocoding, routing, mail, and the AI model provider.

## Database

PostgreSQL 18 with PostGIS and pgvector. `src/db/migrate.ts` creates both
extensions before applying migrations and is safe to re-run, so a retried deploy
converges instead of half-applying.

No published image carries both extensions, so `infra/postgres/Dockerfile`
builds one: `imresamu/postgis` (the multi-arch build of the official PostGIS
image) plus the pgvector package. Multi-arch matters — the official
`postgis/postgis` is amd64 only, which means an emulated, slow database on an
Apple Silicon laptop.

Drizzle's native `geometry` and `vector` column types cover PostGIS and
embeddings, so there is no custom type glue. Geometry columns are real
geometries, not latitude/longitude pairs — map layers are served as Mapbox
Vector Tiles generated by `ST_AsMVT` in the database rather than as thousands of
DOM markers.

Schema files are split by bounded context under `src/db/schema/` and re-exported
through the barrel, which is what both Drizzle and the Better Auth adapter read.
`src/db/schema/auth.ts` is generated by `bun run auth:generate` — edit
`src/lib/auth.ts` and regenerate rather than editing it by hand.

## Identity

Three tiers, because the contest asks the platform to serve tourists as well as
residents:

| Tier | How they get there | What they can do |
| --- | --- | --- |
| `visitor_anon` | No account | Browse the map |
| `visitor` | Email or passkey | Review, upload photos, report traffic |
| `citizen` | Verified cédula | Also vote, open consultations, register a business |

**Planned.** `requireMember()` and `requireCitizen()` will enforce the split, and
upgrading from visitor to citizen must preserve everything the account already
created.

`src/lib/jce.ts` looks a cédula up in the civil registry. It returns a
`found | not_found | unavailable` result rather than throwing, because the
registry is a government service that goes down and rate-limits: onboarding
degrades to "verification pending" instead of locking a citizen out. A
successful lookup proves the cédula exists — never that the person entering it
owns it.

## Planned

- **Map** — MapLibre GL with a custom style, deck.gl for heatmaps and
  choropleths, MapTiler for the demo with a self-hosted PMTiles path for handoff.
- **Background jobs** — pg-boss in its own container: weekly PDF reports,
  notification fan-out, traffic-report expiry, JCE retries, embedding backfill.
- **Reports** — an internal route rendered to PDF by Playwright, so screen and
  print share one render path.
- **Realtime** — Postgres `LISTEN/NOTIFY` into an SSE broker.
- **Offline** — Serwist app shell plus a Dexie queue with idempotency keys, for
  a rural province with intermittent connectivity.
- **AI** — Transformers.js embeddings locally into pgvector; the report
  narrative behind a provider abstraction with a deterministic template
  fallback, so the platform costs nothing to run without an API key.
- **i18n** — next-intl with `[locale]` routing. Every user-facing string lives
  in `messages/es.json`; nothing is hardcoded in JSX, so adding a language is
  adding a JSON file.
